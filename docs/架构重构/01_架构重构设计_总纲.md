## 1. 为什么重构(第一目的:治"心里没底")

现状三个不满:后端不是想要的、前端不理想、功能缺失。但**真正的根因**是:

> 之前全交给 AI,owner 自己没去理解,**心里没底**。

所以本次重构的**头号成功标准不是"代码更好",而是"owner 能把整个系统装进脑子里、对每一块都有底"。**

**采取的路径**(owner 定):
- **owner 自己设计架构**(自己设计的才真懂),Claude 在**现有能跑的代码上做迁移**,不推倒重来。
- 迁移 > 重写:保住已趟过的坑(多租户、状态恢复、providers)。
- 过程护栏:Claude 不在迁移里替 owner 做一堆看不见的小决定,否则"心里没底"会爬回来。

**风险前提**:owner 脑中架构与现有代码的距离,决定这是"便宜的迁移"还是"偷偷的重写"。距离通过 §4 映射表持续评估。

## 3. 目标架构(owner 设计)

### 3.1 全景:四层 + 两柱

```
┌──────────────────────────────────────────────────────────┐
│  外层定位:整个是一个大项目,"做视频""漫剧"各是一个子项目      │
└──────────────────────────────────────────────────────────┘

   页面交互(前端)
        ↓
   API 层          与用户实际业务绑定;鉴权、校验、
        ↓          把"用户要做X"翻译成"跑X配方"、写业务记录
   业务配方/场景     ← 不同业务的差异放这里(数据,不是代码)
        ↓          mv=一份配方, mv2=另一份, 漫剧=另一子项目的配方
   控制器(引擎)     通用编排解释器,只有一个,所有业务共用;
        ↓          读配方→按步调底层→管状态/重试/恢复
   基础功能         最底层原子:文生视频 / 参考图视频 / 图片生成
                   只管"生成",不管业务

  ── 横切两根柱子 ──
  · Supabase = SSO 单点登录(身份源,跨所有子项目)
  · MySQL   = 业务库 + 注册表(权限源 + 上帝视角)
              页面入口、API 入口、积木、业务配方 全部登记于此
```

### 3.2 各层职责

| 层 | 负责 | 不负责 |
|---|---|---|
| 页面交互 | 用户操作界面 | 业务逻辑 |
| API | 你是谁(鉴权)、请求合法性、翻译成"跑哪份配方"、写 MySQL 业务记录 | 视频怎么生成 |
| 业务配方 | 承载"不同业务的差异"(步骤编排 + 规则 + prompt + 参数引用) | 不写通用机制,不写生成实现 |
| 控制器(引擎) | 读配方照着跑、状态落库、重试、恢复;业务无关 | 不知道任何具体业务(如"mv 要先分镜") |
| 基础功能 | 纯生成原子能力 | 不管业务、不管编排 |

### 3.3 三把尺子(拿不准某段逻辑放哪层,问这三句)

1. **"改用命令行、不走网页,这段还需要吗?"** 需要→控制器/底层;只跟 HTTP/网页/登录有关→API。
2. **"这段 mv 和 mv2 会不一样吗?"** 会→业务配方;完全一样谁用都这样→控制器引擎。
3. **"这段在管'谁/权限/请求长啥样'吗?"** 是→API。

## 5. 业务配方怎么实现(§4 D7 的展开)

**三样东西分开:**

| 东西 | 是什么 | 形态 |
|---|---|---|
| 积木(block) | 有统一输入/输出契约的步骤,内部调基础功能 | 代码 + 注册表 |
| 配方(recipe) | "哪些积木、按什么顺序拼"的装配图 | 数据(YAML/JSON,存 MySQL) |
| 引擎(控制器) | 照装配图施工的解释器 | 代码,唯一,业务共用 |

### 积木库(代码)

```python
@block("storyboard")   # 分镜
def storyboard(brief) -> {"shots": [...]}: ...
@block("keyframe")     # 关键帧图
def keyframe(shot, style) -> {"frame": "xxx.png"}: ...
@block("i2v")          # 图生视频(基础功能)
def i2v(image) -> {"video": "clip.mp4"}: ...
@block("pose_deid")    # 参考视频去身份化(= 现 ad2 的 pose_reference_from_video)
def pose_deid(ref_video) -> {"skeleton": "pose.mp4"}: ...
@block("stitch")       # 拼接成片
def stitch(clips) -> {"video": "final.mp4"}: ...
```

### mv 配方(数据)

```yaml
name: mv-agent
inputs: [song, style_ref]
steps:
  - id: sb
    block: storyboard
    in:  { brief: $inputs.song }
  - id: kf
    block: keyframe
    foreach: $steps.sb.shots
    in:  { shot: $item, style: $inputs.style_ref }
  - id: clips
    block: i2v
    foreach: $steps.kf
    in:  { image: $item.frame }
  - id: final
    block: stitch
    in:  { clips: $steps.clips }
outputs: { video: $steps.final.video }
```

### 引擎(代码 · 概念上就这么点)

```python
def run(recipe, inputs):
    ctx = {"inputs": inputs, "steps": {}}
    for step in recipe.steps:
        blk = REGISTRY[step.block]
        if step.foreach:
            items = resolve(step.foreach, ctx)
            ctx["steps"][step.id] = [blk(resolve(step.in, ctx, it)) for it in items]
        else:
            ctx["steps"][step.id] = blk(resolve(step.in, ctx))
        save_state(ctx)          # 每步落库 → 可中断可恢复
    return resolve(recipe.outputs, ctx)
```

**引擎不知道"mv 要先分镜"——那是配方告诉它的。** 引擎业务无关,永不为新业务改动。

### 变体有多便宜

- **mv2**(参考视频前插去身份化):只在配方里加一步 `pose_deid` + 换个接法。
- **漫剧**(独立子项目):新配方 + **引用共享资产**(不复制人设):
  ```yaml
  - id: render
    block: keyframe
    foreach: $steps.panels
    in:
      panel: $item
      character: asset://character/女主-001   # 引用资产库,不复制
      style:     asset://style/都市漫画风
  ```

### 护栏

**配方只"拼"不"算"。** `foreach` / `$引用` / 顶多一个 `when:` 够了。需要真正逻辑判断的,写进积木内部(代码),不能爬进 YAML。**判据:配方一眼看完就懂在拼什么。**

## 6. 漫剧数据模型要点(§4 D6 展开)

漫剧比独立视频多两样,**都不放配方,放 MySQL 数据、配方按 ID 引用**:

- **层级结构**:剧 → 季/集 → 场 → 镜/格。
- **跨集共享资产**:角色人设 / 画风 / 场景 / 道具。

**⚠️ 找漏(最关键)**:人设/画风**绝不复制进每份配方**,必须做共享资产库、配方只写 `character_id`。否则:①改一次人设要改 N 份配方;②跨集一致性失控(第 3 集女主换脸)。**漫剧成败 = 跨集一致性 = 资产集中管理 + 引用。**
