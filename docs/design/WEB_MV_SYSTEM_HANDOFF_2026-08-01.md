# 本地 MV WEB 系统开发交接文档

> 更新时间：2026-08-01（Asia/Shanghai）
> 目的：把当前 WEB 系统的目标、实际进度、已实现功能、真实可用性、已知故障、业务设计错误、技术债和接手顺序完整交给下一个模型。
> 重要：本文描述的是当前工作树和 `qingyi2` 实测状态，不等同于正式验收报告。工作树存在大量未提交修改，严禁通过 reset、checkout 或覆盖文件的方式“恢复干净”。

## 1. 先读结论

当前系统已经具备一个本地单用户 WEB 工作台的骨架，也已经连接真实 LLM，能够导入项目素材、读取带时间和人物关系的 Excel 歌词、生成音乐/故事/分镜数据、展示并编辑中文提示词、记录 LLM 费用、执行人工拍板，并提供背景和组合首帧的上传/生成入口。

但它还不是可交给普通用户完整测试的成品，核心原因不是少量界面瑕疵，而是生产业务模型仍有错误：

1. 背景被错误设计成“逐镜资产”，没有先建立场景组和背景复用关系。
2. “人物＋背景组合首帧”的来源、用途、依赖关系和费用没有解释清楚。
3. 背景生成入口放在每张分镜卡内，用户面对大量分镜不知道为何生成、生成多少、哪些镜头可以复用。
4. 最新一次 GPT-image-2 背景生成在图片调用前失败，页面返回 423；当前没有生成任何图片，也没有产生图片费用。
5. 浏览器看到的“模型流式生成中”不代表浏览器能看到实时模型输出。后端请求上游使用 SSE，但前端仍等待整个 HTTP POST 返回。
6. 视频 Provider 未配置，Whisper 未配置，因此从真实素材到真实 AI 视频成片的全流程未跑通。
7. 2026-08-01 晚间盘点时，`http://127.0.0.1:8792` 曾短暂无法连接，最终复查又恢复为 ready；瞬时中断原因尚未诊断，服务/重启可靠性不能视为已验证。

在继续写代码前，应先与用户确认“场景组 → 背景母版 → 逐镜组合首帧 → 单镜视频”的业务模型。不要在现有逐镜背景结构上继续补按钮。

## 2. 产品目标与用户已经明确的要求

### 2.1 产品目标

系统以歌曲、歌词时间轴、人物立绘和其他项目物料为输入，在不改变人物外貌、服装和立绘风格的前提下，结合歌曲风格与歌词内容，制作视觉丰富、音画匹配、可人工逐阶段确认的 MV。

长歌词段或长分镜不能用简单静态画面凑时长，应通过叙事动作、构图变化、景别、镜头运动、环境状态和节奏设计提供足够的视觉变化。

### 2.2 用户已经明确的交互和工程要求

- 普通用户需要的路径、Key、URL、模型名都能在页面配置。
- 启动时自动读取已有配置；已有值显示真实状态，Key 仅显示部分脱敏内容。
- FFmpeg、FFprobe、Whisper 等技术概念不能要求普通用户理解，系统应自动识别并用中文状态说明。
- 高级设置中的工作区可修改，修改后明确提示需要重启；页面有重启按钮。
- 页面可见文字应为中文。用户修改中文内容后，系统内部可调用 LLM 转为英文执行稿。
- 所有页面触发的 LLM 请求必须流式。
- 每一步的系统提示词和任务提示词都应在对应步骤中展示并允许用户修改，不能集中放在脱离流程的 PROMPTS 区域。
- 前后端错误日志按天分别记录，用户在页面能看到日志路径。
- 运行记录和费用明细必须分页。
- 图片按 0.5 元/张；视频按 0.6 元/秒。
- LLM 费用公式：

```text
(输入 tokens / 1,000,000 × 5
 + 缓存读取 tokens / 1,000,000 × 0.5
 + 输出 tokens / 1,000,000 × 30) × 0.04
```

- 每个项目显示本次制作总成本，并能追溯每一步的 LLM、图片、视频、翻译、失败和重试费用。
- 新建素材分析任务时不让用户手填路径，应使用文件夹选择器；用户把所有项目物料放在同一文件夹，系统自动识别。
- 人物重复素材应允许从当前项目移除，并使依赖它的故事/分镜结果失效。
- 项目可以彻底删除，但必须有明确确认和路径安全保护。
- 用户要求最终测试必须走真实浏览器、正式页面、真实 Provider 和真实项目产物；本轮交接不进行全面验收。

## 4. 当前已实现功能及真实程度

### 4.1 项目和素材

已实现：

- 创建项目、项目列表、选择项目。
- 选择整个素材文件夹，浏览器逐文件上传，不要求用户填写本地路径。
- 自动分类音频、歌词、人物图和背景/场景图。
- 支持 `.xlsx`、`.lrc`、`.txt` 歌词；`《青衣》歌词分句.xlsx` 中的时间和人物关系能进入 intake。
- 校验一个音频、一个歌词文件、至少一张人物图。
- 人物图可移入项目内回收区，操作可恢复，并使依赖阶段失效。
- 项目彻底删除，要求输入项目标识确认，并带项目目录越界和符号链接保护。

限制和风险：

- 浏览器文件夹选择并不是把文件夹路径交给后端，而是把每个文件复制上传到工作区。大素材文件夹会产生较长上传时间和额外磁盘占用。
- 当前分类依赖扩展名、名称和目录名规则，不能保证任意用户文件命名都能准确分类。
- 导入过程逐文件请求，不是一个原子事务；中途失败可能留下已导入的部分文件。
- 当前没有导入前清单确认、重复文件/哈希去重、预计空间占用或断点续传。

### 4.2 音乐、歌词和分镜规划

已实现：

- 读取音频信息和歌词时间轴。
- 保留 Excel 中的歌词分句、开始/结束时间、出场人物和来源行号。
- LLM 分析歌词语义、人物关系和视觉总谱。
- 结构规划器可把过长歌词段拆为较短镜头，并保留 Excel 人物绑定。
- 页面展示音乐段落、故事框架、人物关系和逐镜数据。
- 失败任务存在从安全检查点继续的接口。
- 故事和分镜进入下游前需要用户确认。

限制和风险：

- 早期版本没有正确利用 `《青衣》歌词分句.xlsx` 的人物和时间数据，后来才补入；需要接手者复核所有下游是否真正消费这些字段，而不只是页面显示。
- LLM 曾多次返回截断或无效 JSON，也发生过超时。虽然加入了一次有上限的重试和费用恢复，真实稳定性仍不足。
- 当前视觉总谱提示词有所增强，但尚未经过用户认可的专业性审查。
- 尚未建立“每个长镜头内部的视觉事件密度”可编辑结构，现有镜头描述不等同于可执行的丰富动作编排。

### 4.3 提示词

已实现：

- 提示词放到对应阶段内，不再只有独立 PROMPTS 区。
- 每个调用步骤展示中文系统提示词和中文任务提示词。
- 提示词可编辑并保存到项目级配置。
- 页面还可查看提示词中译英步骤的系统提示词和任务提示词。
- 中文页面内容可通过 LLM 生成英文内部执行稿，并记录翻译 usage 和费用。

限制和风险：

- 用户尚未确认当前每段系统/任务提示词足够专业、完整。
- 同一个通用翻译环节被多个生成步骤复用，失败会阻断后续生成。
- 提示词版本、变更人、变更时间、回滚和“本次运行实际使用哪一版”还不完整。
- 页面保存中文并生成英文执行稿是长耗时同步请求，缺少清晰的逐项进度和失败恢复体验。

- FFmpeg 和 FFprobe 自动探测。
- 工作区修改后提示重启，页面有“重启服务”按钮。

- 图片成功按 0.5 元/张，视频成功按 0.6 元/秒。
- 可按步骤、任务和分镜聚合。
- 运行记录和费用明细在前端每页 10 条分页展示。

## 6. 最新明确故障：GPT-image-2 背景生成

用户操作：在 `qingyi2` 分镜 S001 点击“用 GPT-image-2 生成背景图片”。

后端日志：

```text
2026-08-01T21:04:50+08:00
POST /api/v1/projects/project-3531246c03670d497567f9eae3ddf2e6/shots/S001/background/generate
423 ApplicationBlocked
message: image prompt translation failed
```

前端日志/提示：

```text
生图提示词翻译失败，请查看错误日志后重试
```

已知调用链：

```text
点击生成背景
→ 校验故事已批准
→ 读取分镜、歌词、人物、上下镜连续性等上下文
→ 调用 LLM 把中文生图指令翻成英文
→ 这里失败
→ GPT-image-2 尚未调用
→ 不产生图片费用
```

当前可以确定：

- LLM 和图片配置字段均已读取并显示 ready。
- 故障不是“没有填写 GPT-image-2 Key”。
- 图片 Provider 尚未真正执行。
- 后端用统一 `ApplicationBlocked("image prompt translation failed")` 包装了底层异常。

当前不能确定：

- 上游是超时、HTTP 4xx/5xx、SSE 格式不兼容、usage 缺失、无效 JSON，还是模型拒绝。
- 失败的翻译调用是否被上游实际计费；因为异常没有携带可恢复 usage，当前本地账本无法确认。

需要修复：

1. 为图片提示词翻译记录底层错误类别、HTTP 状态、Provider、模型、request_id、finish_reason 和可用 usage，仍需严格脱敏。
2. 在前端显示明确阶段：“正在整理中文指令 → 正在翻译执行稿 → 正在调用图片模型 → 正在保存”。
3. 翻译失败应能单独重试，不应把整个生成动作变成无法诊断的 423。
4. 评估是否真的需要每次生图前额外调用 LLM 翻译；可保存已批准的英文执行稿并按内容哈希缓存，避免重复费用和故障点。

## 7. 刚刚确认的核心业务设计错误

### 7.1 当前错误模型

当前代码把背景记录在：

```text
shot_references.shots[shot_id].background
```

这意味着背景天然属于具体分镜。页面也在每张分镜卡里放背景选择、上传和生成按钮。面对 25 个分镜，用户会自然理解为需要逐镜生成背景，既昂贵又没有叙事资产复用逻辑。

### 7.2 应采用的业务模型

```text
故事与分镜确认
  → 系统把所有分镜归并为 3-8 个场景组
  → 用户确认、合并、拆分、改名和调整分镜归属
  → 每个场景组生成或上传 1-3 张背景候选
  → 用户选定背景母版
  → 每个分镜引用背景母版，设置构图变体
  → 每镜生成或上传人物＋背景组合首帧
  → 用户确认逐镜首帧
  → 单镜视频生成
```

建议的数据实体：

#### 场景组

- 场景 ID 和中文名称。
- 地点、时段、天气、叙事世界状态。
- 色彩、光线、材质和画风锚点。
- 对应歌词、情绪、能量和故事功能。
- 使用该场景的分镜列表。
- 允许用户合并、拆分和调整归属。

#### 背景母版

- 属于一个场景组，而不是属于一个分镜。
- 来源：系统生成或用户上传。
- 模型、提示词版本、参考素材、费用、创建时间。
- 候选状态和最终选择状态。
- 明确显示被哪些分镜复用。

#### 逐镜背景变体

- 引用背景母版。
- 只保存该镜的景别、机位、裁切、光线状态、局部道具和必要的环境变化。
- 只有地点、时间、天气、叙事世界或关键情绪状态实质变化时才新建背景母版。

#### 人物＋背景组合首帧

- 属于具体分镜。
- 引用一个背景母版/背景变体。
- 引用本镜人物源图。
- 固定人物身份、服装、站位、遮挡、景别、光线和构图。
- 来源：系统生成或用户上传。
- 是视频模型的完整场景第一帧，不是另一张人物立绘，也不是背景图。

### 7.3 页面入口应调整

- 新增独立“场景与背景”环节，位于故事/分镜确认之后、关键帧之前。
- 背景生成入口从每张分镜卡移到场景组资产区。
- 分镜卡只负责选择场景/背景母版和编辑本镜构图变体。
- “人物＋背景组合首帧”保留逐镜生成，因为人物站位和构图通常逐镜不同。
- 所有生成资产标注：系统生成/用户上传、引用关系、模型、费用、生成时间和选中状态。

### 7.4 尚待用户最终确认的产品参数

- 场景组是否由系统自动建议，用户可自由合并、拆分、改名。
- 每个场景组默认生成几张背景候选，建议默认 2 张。
- 每镜默认生成几张组合首帧候选，建议先 1 张，按需补生成，避免 25 镜一次产生大量费用。
- 背景复用时允许哪些变体：裁切、景别、机位、光线、天气局部变化、道具变化。
- 是否所有组合首帧逐镜人工确认，还是支持批量确认后抽查。
- 生成前是否显示本批预计费用并要求确认。

## 8. 流式能力的真实状态

当前 `SemanticOpenAIProvider` 会向上游发送 `stream: true`，读取 SSE chunk，累计 `content/reasoning_content`，并读取最终 usage。这满足“后端到上游使用流式协议”。

但浏览器调用 `/director/plan`、内容本地化和图片生成时，FastAPI 会在线程池中等待任务全部完成后一次返回 JSON。前端只是把按钮文字改成“模型流式生成中”，没有 EventSource、WebSocket、fetch readable stream 或逐阶段事件输出。

因此当前状态应表述为：

```text
上游 LLM 传输：流式
后端到浏览器：非流式，长请求等待
浏览器实时内容/进度：未实现
```

接手时不能仅检查 `stream: true` 就宣称用户要求已完成。至少需要后端任务化和 SSE/流式事件接口，使用户看到当前步骤、增量内容、usage 到达和失败位置；刷新页面后还能恢复任务状态。

## 11. 其他未被用户明确指出但必须处理的问题

### 11.1 普通用户体验

- 缺少首页级“下一步该做什么”的唯一主操作，虽然阶段中陆续补了按钮，整个链仍需要逐阶段重新审视。
- 错误信息仍以 HTTP 语义或笼统文案为主，用户不应看到 `conflict`、`application error`、423 等内部概念。
- 长任务缺少可恢复的实时进度、取消、重试单步和预计剩余时间。
- 资产较多时，页面一次渲染全部分镜和图片，可能造成性能和滚动负担。
- 没有项目级制作预算、批量操作和变更影响预览。

### 11.2 数据模型和可追溯性

- 背景尚无场景组实体，当前数据库/JSON 引用模型需要迁移。
- 提示词、中文显示稿、英文执行稿、生成资产和费用之间缺少完整版本链。
- 重跑后旧产物、旧费用、当前选中版本的关系需要更清楚，避免用户看到过期结果。
- 失败调用是否收费依赖上游是否返回 usage；无 usage 时只能标为“费用未知”，不能武断写 0 成本。
- 页面分页应最终下沉为 API 游标/分页，而不是全量加载后切片。

### 11.3 安全和部署边界

- 当前是本机单用户工具，没有登录、权限、多租户隔离、CSRF 设计或远程部署加固。
- API 能读取和写入工作区中的项目文件，必须继续保持 realpath、符号链接和目录越界保护。
- Key 保存在本地配置并注入进程环境；需要确认文件权限和备份策略，严禁写入日志或项目导出包。
- 若未来允许局域网访问，当前信任模型不够，不能直接绑定 `0.0.0.0` 给多人使用。

### 11.4 生产质量

- 生成按钮存在不等于视觉方案成立。系统还需要场景复用、多样性预算、逐镜视觉事件、人物一致性和连续性门禁。
- 背景提示词虽然包含歌词、人物风格、情绪、构图、光线和上下镜连续性，但在错误的数据粒度上执行，仍会导致重复生成、成本浪费和视觉不统一。
- 当前缺少从背景母版到组合首帧再到视频的清晰可视化血缘。
- 单镜视频生成后必须接入项目规定的 i2v 诊断闭环，不能只判断文件是否生成成功。

## 12. 接手模型建议顺序

### P0：先停止扩功能，锁定需求

1. 与用户确认场景组、背景母版、背景变体和组合首帧四类实体。
2. 画出修改后的阶段顺序和每个拍板点。
3. 确认批量候选数、费用预估和逐镜确认策略。
4. 用户确认后再改数据模型和页面。

### P1：恢复可诊断运行

1. 查明 8792 瞬时不可用的原因并验证稳定启动/重启。
2. 修复图片提示词翻译底层日志，保留 request_id 和可恢复 usage。
3. 单独验证 LLM 翻译 Provider，再验证 GPT-image-2 单张背景，不要直接批量生成。
4. 失败时页面显示具体阶段和可操作的重试入口。

### P2：重构背景资产模型

1. 新建场景组和背景母版数据结构。
2. 为现有 `shot.background` 写显式迁移或兼容读取，不能静默丢失已有数据。
3. 把背景生成从分镜卡移入“场景与背景”工作区。
4. 分镜只引用母版并保存本镜变体。
5. 生成前显示本批预计图片和翻译费用。

### P3：明确组合首帧

1. 在页面解释它是视频生成的完整场景第一帧。
2. 显示来源、背景、人物、提示词版本、模型、费用和状态。
3. 支持系统生成、用户上传、候选选择、按镜重做。
4. 没有已批准背景/人物引用时明确阻止生成。

### P4：真正实现浏览器流式体验

1. LLM 操作改为后台任务。
2. 浏览器通过 SSE 或等价机制接收逐阶段/增量事件。
3. 刷新页面可以恢复运行状态。
4. usage、费用、失败和重试事件进入同一审计链。

### P5：最后统一验收

1. 使用真实项目 `/Users/wmzuo/Desktop/青衣`，通过真实浏览器创建新项目。
2. 从文件夹导入开始，不直接调用后端伪造页面状态。
3. 只生成最少背景候选和 2 个分镜的组合首帧/视频，控制费用。
4. 页面必须能看到真实生成图片、视频、每步提示词、运行记录和费用。
5. 同时检查桌面和移动端布局、所有中文、日志、失败恢复和重启。
6. 两镜合并 MP4 仅作为最小真实链验收，不得标记为完整 MV 成片。
